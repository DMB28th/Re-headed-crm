# MCP Apps review for Cardstack — October 8, 2026

## Architecture answer

**Reusing Cardstack’s custom renderer is technically well aligned with MCP Apps and does not intrinsically require an external UI website. Keeping all runtime hosting in Salesforce remains a conditional architecture, not an established end-to-end result.** The missing proof is Salesforce-hosted MCP ingress, resource serving, OAuth/discovery and real-client interoperability. An HTML renderer and Salesforce’s Hosted MCP/HXL presentation mechanism are separate concerns; this repository does not prove that Hosted MCP can be configured to return arbitrary custom HTML resources.

The existing legacy implementation already uses `@modelcontextprotocol/ext-apps` (`^1.7.4`), `useApp`, `App.callServerTool`, registered `ui://cardstack/...` resources and `_meta.ui.resourceUri`. This is reuse of an existing MCP App, not a migration from HXL into a newly invented protocol. Its React/components can be adapted to the native Apex interaction contract; the old Node server, tenancy/auth system and flow execution code should not automatically become the new runtime. ## What the stable protocol actually provides

1. An MCP tool’s definition contains `_meta.ui.resourceUri`, such as `ui://cardstack/record/v2.html`. That URI identifies a resource on the **originating MCP server**, not a website URL that the browser navigates to.
2. The host calls **`resources/read`** to retrieve that URI. The response contains `contents[]`, matching URI, MIME **`text/html;profile=mcp-app`**, and HTML in `text` or base64 `blob`. A valid HTML5 document is the portable contract. UI-only resources may be omitted from `resources/list`; they still must be readable.
3. The host renders the returned HTML in a sandboxed iframe. Tool arguments and results arrive separately over notifications, rather than being compiled into tenant-specific HTML. UI resources may be cached/prefetched, so version the URI for incompatible bundle changes.
4. The app sends **`ui/initialize`**, receives host capabilities/context, then sends **`ui/notifications/initialized`**. Register handlers before connecting. The host sends complete `tool-input`, followed by `tool-result` or cancellation; partial input is optional and must not authorize critical operations.
5. UI interactions call **`tools/call` via the host**, e.g. `app.callServerTool({name, arguments})`. The host proxies to the originating server and may reject or require approval. Resource reads similarly use `app.readServerResource({uri})`. This avoids placing Salesforce credentials in browser code.
6. `ui/message` can request a conversational follow-up; `ui/update-model-context` supplies app context for later turns, generally replacing the previous update. Neither is a persistence/authorization mechanism. Durable edit/review/confirmation state should remain in Apex.

Sources: [stable resource/discovery/transport contract](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx), [App implementation](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/app.ts), [React starter](https://github.com/modelcontextprotocol/ext-apps/tree/82221c0c8ce7661efa6771c9d461511b1650495f/examples/basic-server-react).

MCP Apps is optional: the client advertises `capabilities.extensions["io.modelcontextprotocol/ui"].mimeTypes`. Tools need meaningful text fallback. Merely speaking core MCP does not imply UI support. `visibility` defaults to `["model","app"]`; `["app"]` hides a tool from the agent while permitting same-server app access. The host must reject app calls to tools lacking app visibility. Visibility is **not** Salesforce authorization. [Stable capability and visibility requirements](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx).

## SDK division of responsibility

| API/module | Responsibility and implication |
| --- | --- |
| `App` / React `useApp` | Connect view to host, receive input/results/context, call server tools/resources, send messages/context, report size. Preserve Cardstack’s bridge abstraction. |
| `registerAppTool` | Registers a normal server tool with UI metadata; current helper also normalizes legacy flat `ui/resourceUri`. It does not provide backend hosting or OAuth. |
| `registerAppResource` | Registers resource read handler and default MIME type. Apex can implement the same wire responses without running this Node SDK. |
| `getUiCapability` | Reads negotiated client UI extension. Check actual capabilities rather than assuming a named client supports every method. |
| `AppBridge` | Host-side communication and optional forwarding to an already connected MCP client. ChatGPT/Claude own this role; Cardstack generally should not ship a chat host. |
| `PostMessageTransport` | JSON-RPC window messaging; validates sender window and message schema. Host must enforce policy beyond transport validation. |

## Security and hosting consequences

All view content must be sandboxed. Web hosts require a different-origin sandbox proxy. Hosts construct CSP from resource metadata, may restrict further and must not allow undeclared domains. `connectDomains` permits fetch/XHR/WebSocket; `resourceDomains` permits assets; `frameDomains` permits nested frames; absent nested-frame permission means blocked. Browser permissions are requests, not guarantees. `_meta.ui.domain` is host-specific sandbox-origin configuration, **not a requirement to deploy a second UI server**. CSP permission and API CORS permission are separate. Prefer self-contained bundles and host-proxied tools for Cardstack, with no Salesforce tokens or record data embedded in static resources. [Stable security](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/2026-01-26/apps.mdx), [CSP/CORS](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/csp-cors.md).

OAuth is the MCP server/host connection’s responsibility. The authorization guide discusses discovery metadata, audience-bound token verification, HTTP 401 challenges and per-server/per-tool authorization. An authenticated CLI call does not demonstrate client discovery, login or browser interoperability. The SDK does not solve Salesforce’s ingress or authorization discovery boundary. [Authorization guide](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/authorization.md).

## Stable, draft and migration caveats

The draft adds/clarifies: content-level `_meta.ui` takes precedence over listing-level metadata; app-provided tools and bidirectional tool discovery/calls; richer host capability declarations for messages/context/sampling; `ui/download-file`; and task-aware long-running app tools. App-provided tools are ephemeral and untrusted: tied to iframe lifetime, with attribution, approval, validation, namespace and resource-limit considerations. These are useful future capabilities, not prerequisites for an ordinary editable Cardstack form, and must not be assumed available in every host. [Draft](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/specification/draft/apps.mdx).

The v2 guide says the main iframe wire protocol remains compatible with v1 hosts/views, while dependencies and TypeScript APIs change: split base SDK packages, Node 20+, Zod 4.2+/Standard Schema and new handler context/error conventions. It separately documents host-side error/schema differences. **No upgrade is required just to investigate reuse of the current v1 Cardstack renderer.** [v2 migration](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/migrate-to-2.md).

OpenAI migration maps `openai/outputTemplate` to `ui.resourceUri`, Skybridge MIME to MCP App MIME, `window.openai.callTool` to `callServerTool`, and globals to async notifications. Some guide details lag source: it claims automatic OpenAI transport detection and references `viewport.maxHeight`, while inspected current `App.connect` defaults to PostMessageTransport and the spec uses `containerDimensions`. The stable spec also describes structuredContent as outside model context; current ChatGPT guidance explicitly uses structuredContent in model workflows. **Do not treat structuredContent as confidential**; avoid secrets in every tool payload. [Migration guide](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/docs/migrate_from_openai_apps.md), [current App source](https://github.com/modelcontextprotocol/ext-apps/blob/82221c0c8ce7661efa6771c9d461511b1650495f/src/app.ts), [ChatGPT UI guidance](https://developers.openai.com/plugins/build/chatgpt-ui).

## Recommended bounded next step

Retain the working HXL adapter and shared Apex policy/interaction services. Treat the old React renderer as a second presentation adapter: bundle static HTML into a Salesforce StaticResource; have a Salesforce-hosted MCP endpoint return it through `resources/read`; translate widget calls to published Apex interaction tools. Keep configuration, identity, sharing/CRUD/FLS, exact typed review, confirmation and receipts in Apex.

Before promoting this to the default, prove in each advertised client: per-user OAuth/discovery; resource fetching and initialize handshake; typed multi-field receipt; preview/confirmed save/read-back; Cancel/Back/retry behavior; and clean-org installation. This is the shortest path to determining whether Salesforce-only custom UI is viable. If the Hosted MCP product cannot serve arbitrary UI resources, investigate the existing custom Apex endpoint rather than assuming metadata alone will make HXL execute React. Any external transport fallback remains an explicit architecture decision. This recommendation is an inference from the protocol plus the dated local evidence, not a Salesforce product-support assertion.
