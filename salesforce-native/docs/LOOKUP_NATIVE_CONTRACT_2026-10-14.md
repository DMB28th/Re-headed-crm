# Salesforce lookup authority contract

October 14, 2026. Documentation-only investigation for the shared Cardstack editor. Canonical integration checkout: `mcp-apps-delivery-proof/Re-headed-crm`, baseline `f6eebd1`; deployment baseline `8f1b138` supplied by the integration owner. Lookup checkout inspected: `dynamic-lookup/Re-headed-crm`, baseline `94035dd`. Target remains `cardstack-spike2`, API **67.0**. These baseline and deployment references are context, not a deployment verification by this investigation.

## Decision and precise blocker

Keep positive lookup capability disabled. Supported native Apex can derive reference schema and perform access-controlled searches and exact-ID reads. The examined API 67 documentation does **not** establish an in-process Apex service that applies the complete effective native lookup restrictions for an arbitrary source record/field and validates a submitted target ID. This is a missing demonstrated authority capability, not a claim that every possible Salesforce API has been exhaustively disproved.

The blocker has three parts: complete effective restriction acquisition/evaluation, current restriction freshness, and exact selected-ID qualification at fresh Review and locked Confirm. A readable target is insufficient. A search result from an earlier interaction is insufficient. Missing filter metadata is insufficient. No product code, org/config/auth changes, deployments, Salesforce writes, or anonymous Apex were performed. Deployment JWT was not touched; the current direction to leave it ON overrides stale disable-JWT deployment guidance.

The UI API is a supported **HTTP suggestion resource**, not an established Apex-native lookup evaluator. Its documented semantics also do not match the frozen minimum-2 `name_tokens` contract. Switching to `Search` broadens matching beyond names; silently switching to minimum 3 changes the approved UX. A future HTTP design requires an explicit contract decision and supported authenticated user-context transport. This investigation did not authorize or create another OAuth/Named Credential route, forward incoming tokens, extract a session ID, or use internal Aura/Flow endpoints.

An ID's absence from a bounded page is not an authoritative negative membership answer. A fresh returned suggestion can provide positive evidence for that request's suggestion semantics. A possible conservative validator could re-request current native suggestions using an exact candidate's readable name, accept only the exact full ID returned in the bounded result, and reject everything else. This produces false negatives for eligible records because of pagination, duplicate names, ranking or indexing; it does not require an exact-ID endpoint to be logically possible. It still needs proof that the specific resource covers all applicable restrictions/special rules, current effective controlling values and the required Review/Confirm timing. No such provider or qualification was proven here. The missing endpoint alone is not the blocker.

## Concrete supported architecture and feasible scope

Preserve the shared Apex editor owner for policy, durable state, review, confirmation, CRM writes and receipts. The lookup provider stays a server-only dependency. Its dynamic source/field definition originates from owner state; the browser supplies only exact query/selection values and correlation. Reuse the completed local picker as a field control, not its independent RecordForm engine.

The inspected `CardstackNativeLookupProvider` already performs schema/access preflight and validates selection syntax/type before throwing `NATIVE_LOOKUP_PROVIDER_UNAVAILABLE`. `resolve` does not read the source record: the owner must verify source existence and sharing in USER_MODE first. No positive descriptor, candidate list or selection is currently emitted. The provider's transaction-local issued definition is not durable authority and must be reconstructed on each request. These are source observations at `94035dd`, not integrated/deployed behavior.

Feasible now: integrate disabled capability behavior, build/reuse presentation mechanics, and implement bounded access-controlled query helpers behind the gate. This does not enable source-field native eligibility. Do not expose the legacy `CardstackLookupSearchAction` as a substitute: caller-selected target search cannot satisfy the contextual boundary.

A conditional Salesforce-only approach is to acquire actual supported Metadata API filter definitions through an explicitly authorized admin path, publish verified semantic snapshots in Salesforce, and implement a strict, documented supported subset in Apex with per-relationship special adapters. This can avoid external runtime hosting and credential extraction. It remains a **custom evaluator of acquired native definitions**, not Salesforce's native lookup engine, and is not a delivered design. It needs affirmative completeness, typed semantics, independently verified special rules, and a supported current freshness mechanism before any field is enabled. Unknown operators/coercions/globals, inaccessible dependencies, absent/incomplete acquisition, drift or expiry must disable it. An old snapshot plus a hash cannot observe current native metadata changes. A generic admin-entered SOQL predicate would substitute Cardstack policy for native restrictions and is unsuitable.

For an ordinary single-target custom lookup, a `verified-none` scope could be established through successful complete authoritative acquisition of that precise field's native definition, an explicit verifier that understands the field's supported relationship semantics and confirms no applicable active restriction, feature/special-rule applicability checks, and current freshness evidence. Tests must establish this acquisition contract with known filtered and unfiltered fixtures, not merely accept absent XML. Once those prerequisites are proven, exact target type/access checks can qualify IDs without an invented filter. This is a bounded avenue to enablement; generic null `filteredLookupInfo`, a once-retrieved component, or absence of a published row cannot establish it.

Another conditional avenue is Apex HTTP callout to the supported UI API using Salesforce-managed per-user Named/External Credentials. Salesforce documents that [per-user OAuth callouts automatically use the current user's token without authentication handling in code](https://developer.salesforce.com/docs/platform/named-credentials/guide/nc-use-oauth-cred-in-callout.html). This could keep runtime execution/credentials hosted on Salesforce and avoid credential extraction. Same-org UI API access, connected-actor equivalence through Cardstack's ingress, permitted scopes, user onboarding and callout ordering/locks require explicit design and API 67 proof. A named principal would weaken the connected-user model. No existing matching configuration was verified, and no new authentication/configuration was authorized or obtained. HTTP lookup support therefore remains a supported platform option with unproved integration, not a forbidden platform capability or a ready fallback.

Finally, native USER_MODE DML at Confirm is the authoritative actual write: access enforcement plus Salesforce save-time required lookup filters and other native save rules. That supports safely attempting a **confirmed** write and handling rejection; it does not establish that the exact ID met lookup eligibility before Review, does not make suggestions filter-correct, and cannot automatically stand in for optional suggestion-filter semantics. A deliberately narrower product contract could rely on save-time qualification, but that would change the current frozen pre-Review/Confirm contract and needs the user's decision. This report does not implement that change.

For the Account.ParentId fixture, an adapter additionally needs verified hierarchy/feature semantics and bounded ancestry checks. The October 12 audit's null describe filter/absent XML is dated acquisition evidence, not proof of unrestricted ParentId today. No fresh org acquisition was performed here. The same discipline applies to Contact.ReportsToId and other special relationships; object-neutral UI does not imply generic relationship eligibility.

## Required implementation handoff

Retain `resolve / describe / search / validateSelection`, with an unavailable result until all authority gates pass. Freeze a current source-field context containing actor/org, canonical source ID/type/field, published policy revision, declared controlling source values, effective reviewed values, supported adapter/version and verified restriction/freshness fingerprint. Nothing caller-supplied may select a target type, filter or dependency field outside that context.

1. **Describe:** only emit lookup presentation after complete current capability and dependency checks. Current supported source/field policy may restrict native eligibility, never expand it. Missing proof remains unsupported.
2. **Search:** derive source identity from shared stored state and read current controlled dependencies under USER_MODE. Apply the same qualified predicate used by exact selection, bounded name-token candidate acquisition, combined ceiling 50 and result ceiling 10. Preserve minimum 2 / maximum 100 UTF-16 units / debounce 300ms until an approved contract change. Search is read-only and neither advances revision nor issues a confirmation grant.
3. **Canonicalization and fresh Review:** validate full checksum18 selected ID, native target type, exact target existence/readability, current native restrictions and special rules using an exact-ID operation independent of query pages. Return only permitted readable display fields. Evaluate dependent restrictions against the effective reviewed source patch, including other changed controlling fields; persisted old values alone are inadequate. Null clearing remains the owner's required/canClear decision.
4. **Locked Confirm:** after the owner reconstructs and locks current state, repeat capability, controlling-value, access and exact eligibility checks. Compare reviewed policy/restriction/freshness binding. Invalidated context rejects before the CRM mutation. The existing owner commits user-mode DML and durable receipt/audit; native save errors still decide races and other Salesforce business rules.
5. **Evidence before enablement:** prove matching and nonmatching required/optional filters, dependency changes within a multi-field patch, source access loss, target access loss/deletion, metadata drift, self/cycle/depth/feature rules for hierarchy adapters, exact-ID tampering and eligible IDs absent from previous suggestion pages. Verify fresh Review and locked Confirm rejection and safe recovery, then real-client picker and Salesforce read-back. Test privileged and ordinary connected users. No existing UI test establishes these backend gates.

Do not use a trial DML update followed by rollback as a read-only qualification service: it would execute a write path during lookup/Review and bypass the owner's explicit confirmation boundary. Do not weaken exact preflight to DML-only save validation merely because final DML is authoritative.
