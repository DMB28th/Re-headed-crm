# Legacy Flow interpreter audit for an Apex port

Audited October 8, 2026. Repository: `/Users/danielben-atar/Re-headed-crm`. This is a read-only source audit and a proposed first execution contract, not an approved implementation spec or a delivered native runtime. Only scratch evidence in this chat's `work/custom-ui-audit/` was added. No application server, dependency install, build, org access, deployment, or CRM mutation was used. Root and native `AGENTS.md` were read. The Apex skill's security/architecture guidance was applied to portability; authoring templates, analyzer-on-changed-Apex, Apex test generation, deployment, and org test execution are N/A because no Apex source was changed.

## Conclusion

Reuse the interpreter's conceptual split (metadata → indexed graph → screen render model → transition → proposed write) and its existing fixture corpus. Reuse the custom form renderer. Do **not** reuse the retired server's stateless, client-carried execution authority or claim Salesforce Flow parity. Port a fail-closed, explicitly published subset into Apex, backed by private durable interactions and the native confirmation/policy services. Browser code should render fields and submit answers; Apex must own graph traversal, variables, validation, targets, review, execution and receipts.

The current native Flow actions are Salesforce launch cards, not the legacy interpreter. `salesforce-native/force-app/main/default/classes/CardstackFlowStartAction.cls:17` describes launch-only behavior and `:75` constructs a Flow URL. `CardstackFlowContinueAction.cls:15` says it does not execute a flow; `:52` merely echoes chat notes. No native interpreted-process result follows from the legacy tests.

## Confirmed correctness and authority gaps

The scratch harness `interpreter-probes.mjs` transpiles current TypeScript source in memory, replaces its local module imports with data URLs, and executes stub effects. It never imports retired `dist` or connects to Salesforce. Captured results are in `interpreter-probes.json`.

1. **Answer submission can change execution context.** Every supplied answer key is merged into the authoritative answer map (`flow-interview.ts:1594`); no current-screen allowlist, type validation or protected-variable namespace exists. Probe changed initially seeded `recordId=ORIGINAL` to `OTHER` and produced a proposed update to OTHER. `action-inputs.ts:85` accepts any defined ask answer (including empty/wrong-type values) while merely labeling its expected valueType. Port must distinguish immutable trusted context, editable input resources and computed resources.

2. **A signed state is reusable write authority, without subject/expiry binding.** Core state contains frames only (`flow-interview.ts:365`), serialized as base64 JSON (`:379`), not encrypted. Server wraps it in HMAC (`server.ts:1544`); signer verifies body/signature only (`apps/mcp-server/src/confirm-token.ts:59`). There is no state-specific actor, tenant, outer record, action session, policy/Flow revision, issued-at/expiry, or consumed receipt. The 5-minute TTL in regular confirm tokens does **not** apply to `signState`. Replaying the same pending-create token in core called create twice. A cancelled legacy interview does not revoke captured state: `server.ts:2160` only acknowledges cancellation. Outer requested flow/policy is checked, but decoded frame.flow drives traversal (`flow-interview.ts:1549`), with no equality binding to outer requested Flow. Sharing a signer across server users/connections therefore needs explicit subject checking, not signature integrity alone.

3. **Preview does not freeze the write definition.** Each continue builds a fresh definition index (`flow-interview.ts:1548`), then recomputes pending assignments from current metadata (`:1575`). Legacy Salesforce adapter re-resolves the currently active version and caches only 60 seconds (`packages/crm-adapters/src/salesforce/salesforce-adapter.ts:1360`). Probe previewed Name=`reviewed`, changed the resolver definition, then confirmed Name=`changed`. Freeze version/compiled plan and the exact review patch; invalidate on publication change. Confirmation ignores new answers on the confirming call, which is good, but insufficient when metadata/formulas themselves change. NOW/TODAY may also change between review and execute.

4. **Write predicate semantics can widen a write.** `targetsOf` finds any Id equality filter and ignores all other filters (`flow-interview.ts:1125`). Probe containing Id=A AND Industry=Impossible still proposed A. Lookup adapter drops unsupported query-filter operators/fields rather than rejecting (`salesforce-adapter.ts:1412`) and joins remaining conditions with AND (`:1421`); core metadata does not represent lookup filterLogic (`flow-interview.ts:118`). Reject unsupported predicates and logical forms before execution; do not interpret omission as consent.

5. **Static `full` support is not executable equivalence.** Analyzer checks element-array category, screen field category and selected top-level formula error strings only (`flow-analysis.ts:66`, `:92`). It does not validate connectors, duplicate names, missing starts, reference existence/type, decision operators/logical forms, assignment operators, processor subtypes, effect availability, child graphs or field-validation formulas. Probes: Recommendation processor + unresolved child + delete graph returned `full`; a VLOOKUP screen-validation formula also returned `full` and reached confirm-write. `full` should become a versioned compiled-subset result after structural and semantic validation.

6. **Unsupported screen fields do not stop server traversal.** `renderField` returns an `unsupported` placeholder (`flow-interview.ts:831`); walk returns the screen normally (`:1338`). Continue checks validation/required answers, not presence of unsupported fields (`:1596`). Probe upload-only screen advanced to confirm-write although analysis was `partial`. Server explicitly starts partial graphs (`server.ts:1652`). An absent PasswordField must never silently allow a downstream write. Reject the entire unsafe graph before starting.

7. **Server screen validation is incomplete.** Unevaluable field-validation formulas are ignored (`flow-interview.ts:1472`) even though source comment claims analysis flags them; analyzer only scans top-level formulas. Required checking ignores same-screen visibility (`:1481`), so probe Toggle=false with hidden required Input stayed on the screen. Required checking reads answers rather than effective default values; all Boolean required flags are skipped. Choice membership, table selected-ID membership/max selection, numeric/date validity, slider bounds and composite fields are not enforced by this core validation. Nested field errors are stored but renderScreen attaches errors only to top-level rendered entries (`:1053`). Defaults and hidden-value retention require an explicit server contract.

8. **Descending loops repeatedly reverse stored data.** `flow-interview.ts:1378` reverses the current collection each iteration; `:1383` stores it back. Probe rows A/B/C/D produced DBBD, expected DCBA. Existing loop test covers ascending iteration only (`flow-interview-elements.test.ts:125`). Fix before enabling loops; proposed first subset excludes them.

9. **Condition logic silently guesses.** `1 OR 2`, uppercase OR, or numbered combinations collapse to AND (`flow-interview.ts:673`, `:789`, `:1237`). Probe true/false with `1 OR 2` selected No while analysis reported full. A matching decision rule with null connector also falls through to default due to `next ?? defaultConnector` (`:1354`). Strictly parse supported forms; a matched terminal outcome must terminate.

10. **Formula parser can return unsafe/incorrect values.** `1/0` returns ok:true with Infinity (`flow-expressions.ts:296`, `:401`), serialized to null by JSON. DATE builds strings without calendar validation (`:183`); probe returned `2026-99-99`. `&&` and `||` share one left-associative precedence layer (`:239`); probe `TRUE || FALSE && FALSE` returned false. Functions evaluate every argument before calling IF/CASE (`:343`), so `IF(TRUE,1,VALUE("bad"))` failed. UTC JS dates, binary floats, Math.round and lexical date strings require chosen semantics, not a literal Apex port. The tokenizer has no source/token/depth limits and recursive references return undefined after depth 10 rather than a typed failure (`flow-interview.ts:543`). Restrict or compile a small AST and reject unsupported forms.

11. **Back/handoff/late errors can misrepresent effects.** Sequential multi-target effects have no transaction rollback (`flow-interview.ts:1188`). Previous writes are not undone when Back revisits a screen, cancelling a later pause says “nothing was written” (`:1572`), and unsupported traversal after a write falls back to a fresh Flow URL (`server.ts:1737`, `:1823`). That URL carries input/context only, not the interpreter cursor. Starting native Flow after partial interpreter writes can repeat work. Legacy audit also uses before:null for updates (`server.ts:1705`). First subset should allow one terminal mutation and no Back after completion; any later extension must define transaction/fault/resume semantics.

12. **Presentation data needs sanitization independent of graph correctness.** Legacy sanitizer removes scripts/style/embeds and event attributes but is not an allowlist of safe tags/attributes/protocols (`flow-interview.ts:466`). Interpolation inserts CRM values into HTML without HTML escaping (`:593`, `:842`), and image link uses unsanitized protocol/label (`:1030`). UI/rendering audit should own robust text escaping and URL/tag policy; Apex may emit typed text/rich-text DTOs rather than arbitrary HTML.

## Native authority to preserve

`salesforce-native/force-app/main/default/classes/CardstackRecordEditService.cls` already shows the right ownership pattern: immutable record/policy context (`:21`), random opaque key with hashed storage and actor/expiry (`:38`), private interaction lock (`:48`), actor/policy/status/expiry/revision gates (`:49`–`:60`), invalidation on Back/Cancel (`:72`), server field/type validation (`:77`), current-record fingerprint before review (`:87`), exact confirmation linkage (`:99`) and repeat-safe Completed handling (`:54`). Its delivered edit contract currently supports Account String/Textarea/Integer (`:18`, `:133`); do not infer Opportunity/date/currency support from the legacy UI inventory.

`CardstackConfirmToken.cls:17` locks stored actor-bound confirmation rows; `:22` checks subject; `:26` checks record freshness; `:29` stores receipts; `:32` includes exact patch and policy revision in subject. `CardstackUpdateRecordAction.cls:37` revalidates published policy, `:41` returns receipt on repeat, and `:46` locks and reads record in user mode. These are useful reusable services and examples, not permission to bypass policy in a new interpreter.

Maintain `with sharing`, explicit user-mode business reads/writes, schema and published-policy intersection, exact input/patch normalization, server-owned current revision, short expiry, stable reviewed values, cancellation, saved receipt, and independent read-back. Internal system-mode access to private interaction/confirmation rows must keep explicit actor checks; it is not a precedent for elevated business-record access. Runtime hosting, ingress/resources, durable state and execution remain in Salesforce. Node/Buffer/HMAC helpers and retired tenant/config infrastructure are not the port destination.

## Proposed first executable subset

This is a concrete candidate contract to approve and implement; it is not present in Apex today.

1. Studio imports/synchronizes a selected active Screen Flow version using a supported, validated ingestion path. Validate and compile it once into a typed published plan stored in Salesforce; record Flow version/hash, subset version and publication revision. Browser never downloads/interprets raw Flow metadata. Metadata acquisition/auth permissions from native Studio still need proof; retired Tooling API use does not establish an Apex ingestion path.
2. Accept an acyclic graph with one explicit start; up to five screens and fifty total nodes, no subflows/loops. Validate unique names, all connector targets, terminal paths, exact property/operator/type shapes and all references before publication. Reject unsupported non-null metadata semantics rather than silently ignoring them. Proposed limits are conservative product limits, not Salesforce governor guarantees.
3. Screens support grouped plain display text, String/textarea, whole-number, Boolean and static single-select inputs, defaults from trusted context/constants/prior supported variables, and Next/Back/Cancel. Save remains limited to published Account String/Textarea/Integer fields through existing native governance. Read-only Boolean/choice inputs may steer decisions; storing them to unsupported native field types requires explicit subsequent scope/testing. Decimal/currency/date/date-time controls are existing renderer candidates for a later expansion.
4. Permit scalar Assign; typed EqualTo/NotEqualTo and numeric comparisons using explicit AND/OR lists; terminal/default decision branches. All data types/refs are compiled. No general legacy formula grammar in first executable release. Permit literal/variable text templates with output escaping; add named tested formula AST operations separately. Any validation expression outside the exact compiled subset blocks publication, never fails open.
5. Permit one current-record lookup by immutable context Id, at most twenty published readable fields. It executes in user mode and errors on unavailable data. No arbitrary query filters, broad collections, dynamic choices or inferred fields. Server initializes defaults as actual answers; validates current-screen input allowlist, types, limits, choice membership, visible-required rules and hidden-answer retention at every submission.
6. Allow a read-only terminal Finish or one terminal record update to that immutable context record. All mapping fields must be explicitly published/editable and describe-writable. The proposed patch is frozen for review and executes only through native preview/confirmation/freshness/receipt services. No create in first cut: first prove record update repeat-safety; later create requires an equally strict stored confirmation and receipt contract.
7. Keep the server protocol small: start(published action identifier, record context), continue(opaque interaction key, expected revision, current-screen answers), back/cancel/resume, review and confirm(current review reference/grant). Model/browser cannot submit cursor, frames, targets, policy, computed variables or mutation payload. Back invalidates old review grants; stale/duplicate operations return authoritative state or a saved completion receipt.

Clearly rejected in first release: delete under all circumstances; creates; bulk and multi-object mutations; nonterminal writes; inputReference SObject/collection write shapes; loops, processors, subflows; waits/async paths/scheduled starts/triggers; Apex/plugins/actions/callouts; transform/rollback/orchestration; custom LWC, passwords, uploads, repeaters, lookups/dependent picklists; multi-select/table selection execution; dynamic choices; general formula/validation syntax; legacy start shapes; unknown metadata properties with executable meaning; system-mode Flow execution. For already unsupported graphs, show a Salesforce launch card **before any interpreter side effect**. That is a new native interview, not continuation of a partially executed custom interview.

## Graph governance and Apex portability

Legacy limits are 1,000 walk steps **per walk call**, 100 lookup rows, 50 displayed table rows, 20 inferred fields per lookup, reference depth 10, three frames and 25 update/delete targets (`flow-interview.ts:440`, `:701`, `:1185`, `:1401`). They do not bound total interview transitions, field nesting, cumulative query/effect count, formula AST size, state byte size or number of query nodes before a screen. A 1,000-step JavaScript budget is not safe Apex governor budgeting.

The proposed native plan must bound both graph size and per-transaction work. Suggested first limits: 50 nodes, 5 screens, 20 total writable inputs, 20 projected fields, at most one lookup and one terminal mutation, 50 internal transitions per advance, 100 interaction operations across lifetime, 64 KiB normalized plan/state each. These are candidate hard caps to benchmark before release. Monitor actual Apex CPU/heap/query/DML consumption with headroom and fail closed before additional effects. Avoid SOQL/DML inside generic graph loops; batch later allowed queries/writes deliberately. Do not silently truncate values, columns or targets.

Port the finite-state machine and typed render DTOs, not JavaScript coercion. Use Apex Decimal/Integer/Date/Datetime/Boolean with explicit conversions/null semantics; typed Map/List structures for variables; a validated immutable node index; frozen published-plan references; a reference cycle detector; explicit terminal/error statuses. Session persistence adds locking and revision safety. Keeping interpretation in Salesforce still implements a subset, not Salesforce's full Screen Flow engine; reject unsupported execution semantics even though Apex could technically call some actions.
