## Declarative Lists editor: feasible UI, missing policy wiring

**Current Studio storage:** `listsKey` is `exposures:{Object}`; the primary Lists textarea stages that JSON and defaults to `{views:[],customLists:[]}`. Search found no authoritative list-runtime consumer of that key in either revision. A UI replacement that merely writes the same value cannot claim visibility, defaults, or aliases influence chat. [Key](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/lwc/cardstackObjectConfig/cardstackObjectConfig.js:196), [draft save](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/lwc/cardstackObjectConfig/cardstackObjectConfig.js:1092), [sample](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/lwc/cardstackObjectConfig/cardstackObjectConfig.js:1338).

**Discovery is available:** `CardstackListViewsAction` queries real `ListView` Id/Name/DeveloperName for the object with `WITH USER_MODE`. This supports an admin picker of views visible to that admin. It does not establish another user's visibility; runtime must independently recheck the connected user's Salesforce rights. [Discovery query](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewsAction.cls:27).

**Execution is a bounded fallback:** `CardstackListViewAction` resolves exact/normalized/fuzzy view names, then uses user-mode filter SOQL. Salesforce names contribute labels and “My …” owner filtering; arbitrary Salesforce saved filters, columns and sorting are explicitly not reproduced. It sets `usedRealView:false` and an explanatory fallback note for explicit named-view requests. A picker must retain that distinction and must not preview a fallback as exact Salesforce view execution. [Resolution and fallback](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:79), [name matching](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:159), [filters and columns](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:299).

**Separate saved Cardstack lists exist:** active `listview:{Object}:{normalizedName}` records store query/stage/openOnly/amount bounds/sort/myOnly, and execution merges permitted request refinements. They are considered only when a Salesforce view does not resolve, so collisions can choose Salesforce-name fallback ahead of the Cardstack saved filter. The runtime writes these active configs directly when native CRUD permits, independently of Studio's `exposures` draft flow. Preserve that data and avoid silently treating it as exposure metadata. [Saved lookup](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:192), [execution](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:211), [save behavior](/Users/danielben-atar/Re-headed-crm/salesforce-native/force-app/main/default/classes/CardstackListViewAction.cls:242).

**Recommended proposal boundary:** replace raw JSON as the primary UI, but include published exposure-policy consumption and validation as explicit implementation work if toggles/defaults/aliases are promised. Keep Salesforce view discovery, exact view execution, and Cardstack saved-filter lists visibly distinct. Do not broaden this UX work into undocumented self-REST or arbitrary saved-view fidelity; the existing runtime explains why Hosted MCP cannot supply an Apex self-REST session. Exact saved-view execution needs its own supported design and proof. Preserve unknown existing configuration keys and saved lists during migration; advanced read-only inspection/export can remain available for unsupported legacy values. Test effective policy with a connected ordinary user, without implying the admin's picker demonstrates that user's access.
