# Legacy governance and runtime gaps worth carrying into native Cardstack

Source inspection on 2026-10-05. This note compares executable source in retired `apps/` and `packages/` against authoritative `salesforce-native/force-app/`. No product changes, org actions, or tests were performed. Old design comments are context, not proof of connector behavior. References are repository-relative filename and line anchors.

## Priorities

1. **Enforce published card policy in preview and write tools.** Legacy `packages/core/src/filtering.ts:115` intersects admin `writeEnabled`, field `editable`, field denylist, and CRM writability. `apps/mcp-server/src/server.ts:1178` calls the same preparation routine for preview/write; it rejects noneditable fields and clearing admin/CRM-required fields (`:1184`, `:1200`). Native `classes/CardstackPreviewUpdateAction.cls:33` and `CardstackUpdateRecordAction.cls:33` check Salesforce field permissions, but neither reads the published layout; the update permits fields solely on `isUpdateable` (`:65`). Native record rendering reads published layout (`CardstackGetRecordAction.cls:59`), but its field rows only serialize API/label/value (`:354`), not required/read-only metadata. Thus the recently added Studio flags are configuration UI, not equivalent runtime governance. Salesforce user mode is already valuable and must remain the permission floor; Cardstack policy should narrow it further. Exact confirmation-value/actor binding is a separate audit, not evaluated here.

2. **Curated views with example phrases and ambiguity handling.** Legacy `packages/core/src/view-exposures.ts:33` defines exposed toggle, aliases and default. Actual runtime resolves only exposed views, rejects an explicit nonexposed selection, shows a picker for ambiguous natural-language asks, and remembers per-user choices (`apps/mcp-server/src/server.ts:865`, `:879`). Native `CardstackListViewsAction.cls:36` exposes the Salesforce-visible list-view inventory; there is no `exposures:` read or alias policy in the two native list actions. Native `CardstackListViewAction.cls:97` does support saved Cardstack filters under `listview:{Object}:{name}` and reports its beta fallback honestly (`:106`). Port the admin catalog, aliases and disambiguation, but do not promise native saved-view fidelity: Hosted MCP self-REST is explicitly unavailable in the current implementation. Legacy custom lists also have richer filters (sets, empty/not-empty, sorting and visibility), `view-exposures.ts:45`, `:72`; inspect native filter scope before choosing a subset. Curated exposure is an additional Cardstack policy, never a replacement for Salesforce sharing.

3. **Connect Home Card configuration to the real home tool.** Legacy runtime consumes published block configuration, supports curated list tiles, recent records and followups, and degrades a broken tile to unknown rather than fake zero (`apps/mcp-server/src/server.ts:979`, `:988`, `:1002`). Its schema has per-block limits and published revision (`packages/core/src/home-card.ts:12`). Native Studio stages `homecard` JSON and previews a title/subtitle/sections model (`lwc/cardstackHomeCardConfig/cardstackHomeCardConfig.js:7`, `:30`, `:65`), while native `CardstackHomeAction.cls:13` hardcodes task/recent limits and `:28` builds fixed tasks, recent objects and pipeline summary without reading `homecard`. This is an implemented editor with an unconnected runtime, not completed parity. Native recents also stop after first object's results (`CardstackHomeAction.cls:60` onwards), so they are not globally sorted recent records across objects. Make configuration actually govern what chat sees, using dynamic data rather than sample numbers.

4. **Restore a previous published version, not merely discard a draft.** Legacy publish snapshots previous live config and increments revision (`packages/config-store/src/memory-store.ts:67`); restoring history is itself a new publish and preserves an in-flight draft (`:84`). Native `CardstackConfigService.cls:122` copies a selected draft to live and marks it Published; `:169` only marks an open draft Rolled Back, leaving live untouched. Published drafts remain historical rows, so a UI could reuse their values, but there is no dedicated revision restore function or revision identity. Also, multiple drafts remain open after publication (`:118`), allowing an older draft to overwrite later state. Add explicit restore and stale-base conflict checks. Native Publish Center already has visual summaries, JSON expansion and bulk publishing; do not claim it lacks diffs. Its layout-specific diff compares field additions/removals/order (`lwc/cardstackPublishCenter/cardstackPublishCenter.js:137`), so changed flags/columns/sections need more precise explanations instead of generic metadata-only text (`:185`).

5. **Consistent actionable error cards and refresh behavior.** Legacy central `asToolError` classifies failure, adds reauth guidance, and adds retry only to reads (`apps/mcp-server/src/server.ts:350`). Native list tools already return renderable failures (`CardstackListViewsAction.cls:22`, `:55`), and preview/update have structured DML errors (`CardstackPreviewUpdateAction.cls:84`; `CardstackUpdateRecordAction.cls:123`). Port a consistent result/error envelope across tools, preserving no-blind-retry writes and honest empty/unknown distinction. This is partial parity, not a wholesale absence of native error handling.

## Already present: retain rather than rebuild

- Salesforce sharing and user-mode queries/DML in record, home and write tools.
- Published-only config reads with staged drafts (`CardstackConfigService.cls:28`, `:63`).
- Native audit storage includes acting user, tool, record, timestamp (`CardstackAuditService.cls:16`); update records before/after and rep/model provenance (`CardstackUpdateRecordAction.cls:132`). Audit UI already supports date/user/tool filters, expandable before/after and CSV export (`lwc/cardstackAuditViewer/cardstackAuditViewer.js:9`, `:61`, `:162`). Audit writes are best-effort (`CardstackAuditService.cls:37`), so do not advertise guaranteed capture. A future flow interpreter should add comparable execution-step/write outcomes and configuration version provenance.
- Native configurable named sections, highlights and 1/2/3-column rendering already exist in `CardstackGetRecordAction.cls:236`, `:324`; preserve that implementation rather than assuming all presentation needs a port.

Do not import Node/Railway hosting, token refresh services, workspace ownership, multi-tenant connection/auth databases, or HubSpot infrastructure. Carry the interaction and governance semantics into Salesforce-native mechanisms.
